# 第4章「仲間スライム、お前の頭の中まで管理するんか！」

## 現行の課題構成（2026-10-25）

- `starter/`：第3章 `solution/` の**JSは一致、HTMLはタイトル差あり**で引き継ぐ（2026-11-03再確認）。関数 `cpuControl(actor, targets)` を注入した状態。
- `task1/`：敵スライムA・Bが、それぞれ最初に選んだ生存対象を倒れるまで狙う。素直な実装例では `Slime.lockedTarget` に対象を保持し、`Slime.chooseTarget()` で更新する。初回は従来の `cpuControl` に従いHPが最も低い生存相手を選ぶ。
- `task2/`：敵A・Bは**連携攻撃**として同じ対象を共有し、敵Cは独立して対象を追跡する。素直な実装例では `Slime.targetLeader` を増やし、BがAの `lockedTarget` を参照する。状態共有の要件が `Slime` に侵入する変更負担を体験する。リセット時は参照を作り直す。
- `solution/`：`TrackingController` が `lockedTarget` と `choose(actor,targets)` を持つ。A・Bに**同じインスタンス**を注入して共有、Cに**別のインスタンス**を注入して独立させる。敵ターンは `enemy.controller.choose(enemy,allies())` を呼ぶ。

## 講義の狙い

第3章の「処理を関数で渡す」を受けて、第4章では「処理固有の状態を誰が管理するか」を考える。課題1で `Slime` に状態を置く実装はその時点で合理的であり、誤答ではない。課題2で状態共有の追加要求が発生すると、`Slime` がコントローラーの事情を扱う設計の変更負担が見える。改善例では状態と処理をコントローラーへまとめ、**同じインスタンスを渡すと共有、別のインスタンスを渡すと独立**することを示す。

「クロージャでも実現可能ですが、今回の要件を考えたとき、インスタンスの方を選択することをお勧めします」。クロージャも適切な解法として認める。DIはインスタンス渡しに限定されない。設計の優劣を断定せず、責務と変更負担を比較する。

RPGは講義目的を説明する題材である。A・Bの連携攻撃という軽い設定のみ付与し、ゲームの自然さのために講義内容を変更しない。

## 継続する仕様と検証

単一 `characters` 配列、`team` による敵味方抽出、動的キャラクターカード、ターンログ、味方の関数注入、仲間スライムの操作切替は維持する。課題1・2では敵ターンも注入された `controller` を `chooseTarget` 経由で呼び、第3章の関数注入を捨てない。改善例では敵のみ状態付きオブジェクトを使い、味方は関数のままとする。

**注意**：課題1・2は一つの素直な実装例であり、必ずこの形で書かせるものではない。課題1で別の適切な責務分離を行った受講者が課題2で困らないことも正解として扱う。従来の「4か所対1か所」は新仕様に適用しない。実ブラウザ操作・受講者の負担感は引き続き要検証。
