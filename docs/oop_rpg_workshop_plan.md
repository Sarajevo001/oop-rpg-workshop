## 1. 企画の目的と思想【合意済み】

JavaScriptの基礎を理解した参加者が、単純なRPGの改修を通じて、**修正箇所が多くて面倒くさいという不満**を実感し、その直後に先人が蓄積してきた設計上の工夫を知るハンズオン。

- 「オブジェクト指向開発」を、名前を覚えて従う万能の方法論として扱わない。
- 技術は、実際の不便や問題を減らすために発展した道具として扱う。
- 参加者に高度な設計能力や「設計とは何か」を語る能力を要求しない。無意識に行っている設計判断を出発点にする。
- 目標は課題の完成ではない。**「何か所も修正するのが嫌だ」→「その面倒を減らす工夫があるのか」**という体験。
- 参加者に自力で設計原則を発見させる必要はない。合理的だが後の変更に弱い実装を試す経験を重視する。
- 最後に、複数の工夫の共通した動機を明かす。締めの台詞案：**「オブジェクト指向開発ってね、こういうことなんですよ」**。
- 技術の使いどころを間違える例として「チェーンソーでキャベツの千切り」「火炎放射器でタバコに火を点ける」を使う構想。パターンの機械的適用や過剰設計への戒め。

## 2. 対象者・環境【概ね合意済み】

- 対象：変数、関数、if文などのJavaScript基礎が分かり、電卓程度の単体ブラウザアプリを作れる人。オブジェクト指向の知識は前提にしない。
- 各自ノートPCを持参し、ローカルのJavaScriptをブラウザで実行する。
- 題材：シンプルなRPG戦闘ゲーム。架空の仕様なので追加要求を柔軟に作れる。勇者、敵、HP、武器、魔法など直感的な概念を使用。
- UIや画面表示の土台は配布側で用意し、設計課題と無関係な画面実装で時間を消費させない方針（詳細未確定）。
- 開催時間は150〜180分程度を仮置き。主催者への提案は、教材と時間配分の検証後。

## 3. 教材設計・誘導の原則【合意済み】

1. **一本道**：4章を順に進める。個人別の別ルート課題は設けない。
2. **合理的な近道**：講師は「HPが複数必要ですよね？」のように事実として正しいヒントを出し、配列化など当面は正しく動く方法を連想させる。嘘の説明やバグで困らせない。
3. **後続の要求で負担が顕在化**：修正箇所・繰り返し作業が増える追加仕様を与える。参加者が設計の欠陥を言語化できる必要はない。
4. **イラッとの対象を限定**：狙うのは「同じような箇所を大量に直さないといけない」不満。「問題文が分からない」「環境が動かない」「教材にバグがある」は狙わない。
5. **未完成で終了可**：制限時間に達したら打ち切ってよい。完了率より、想定した負担に到達したかを観察する。
6. **先回りした正解は認める**：「あ、それ、正解です」で受け止め、講座の進行を分岐させない。想定外の合理的実装を否定しない。
7. **章ごとに共通ベースへ復帰**：講師が提示する解決例を説明し、次章は全員が同一の配布コードから開始。各自の実装差を累積させない。
8. **解決策の効果を見せる**：改修前後の変更箇所数・作業量・影響範囲を比較する。可能なら改善後に同種の変更を短く体験させる。
9. **正解の押しつけを避ける**：複数の妥当な設計があり得ることを認める。紹介する技術が唯一解とは言わない。

## 4. 章構成【仮案：コード検証前】

### 第1章：同じ処理を何度も書かせるな！

- **学習目的**：共通関数化。重複した処理を一つにまとめ、仕様変更時の修正箇所を減らす。
- **開始状態**：勇者とスライムの単純な戦闘処理。
- **初回改修**：敵の種類を増やし、類似する攻撃・ダメージ表示処理を追加。
- **ヒント案**：「この敵も、基本的には同じ攻撃処理で良いですよね？」
- **追加入力・改修**：ダメージ計算ルールを一斉に変更。
- **想定する実装**：敵ごとに類似コードをコピーし、個別に修正。
- **狙うイラッと**：「同じ計算を何か所も修正するんか！」
- **解説**：共通関数に集約し、修正箇所を減らす。単純な行数削減だけでなく変更影響の集中を説明。
- **歴史候補**：サブルーチンや処理の分割・再利用の発展。特定の人物・引用は未選定。
- **検証課題**：第1章で参加者が初めから共通関数を作ってしまう割合、重複修正量が十分か。

### 第2章：データと処理をバラバラにするな！

- **学習目的【方向性を再確認・2026-10-22】**：**「そもそも、このデータと処理は誰が管理すべきなのか？」**と考えるきっかけをつくる。データと処理の責務をどう割り当てるか、関連する状態と振る舞いをまとめることが変更時の負担をどう減らすかを体験する。
- **学習上の焦点**：並行配列そのものの欠点を教える章ではない。狙う「イラッと」は、責務が適切に整理されていないために、関連する状態や処理をあちこち修正・確認する煩わしさ。
- **開始状態**：第1章の共通関数化済みコードを引き継ぐ（継続）。
- **具体的な初回改修・ヒント・追加改修・改善例【再検討中】**：現時点で確定しない。受講者に何を気づかせるかを先に定め、その体験を生む方法は柔軟に検討する。クラス構文や特定のデータ構造を唯一の正解として誘導しない。
- **既存案の扱い【保留・履歴として保存】**：味方の複数化、HP等の並行配列化、味方の追加・削除、戦闘不能・被ダメージ・回復処理によって配列の同期負担を体験する旧案は、現行の学習目的と十分に一致しないため、**採用を保留**する。詳細は本書の改訂履歴と既存の第2章コードを参照。コードは比較素材として保持し、教材の確定版とは扱わない。
- **重要な注意**：オブジェクトリテラル、クラス、ファクトリ関数等の複数の妥当な設計を認める。「データを一緒にしたからクラスが必須」とは説明しない。責務の分け方は具体的な要求に照らして判断する。
- **歴史候補**：Simulaなど、状態と振る舞いを持つ対象を表現する考え方。人物・年・原典は未確定。

### 第3章：行動が増えるたびに既存コードを直すな！

- **学習目的**：関数渡しによる振る舞いの差し替え。
- **開始状態**：第2章の共通クラス化済みコード。
- **初回改修**：通常攻撃に加え、炎・氷・回復などの行動を増やす。
- **ヒント案**：「攻撃の種類が分かれば、処理を切り替えられますよね？」
- **想定する実装**：行動の種類をif/switchで判定する分岐を増やす。
- **追加改修**：さらに新しい行動を複数追加。
- **狙うイラッと**：「新しい技が増えるたびに既存の分岐を直すんか！」
- **解説**：実行する関数を外から渡し、実行側を変更せずに新しい振る舞いを加える。
- **重要な注意**：高階関数はオブジェクト指向固有の発明ではない。歴史紹介では関数型プログラミング等との関係を混同しない。
- **検証課題**：初心者にとって関数渡しが理解可能か、分岐を追加する方が実際に面倒になる仕様か。

### 第4章：勇者に武器の事情まで管理させるな！

- **学習目的**：状態と振る舞いを持つインスタンスの受け渡し、責務分担、DIへの導入。
- **開始状態**：第3章の関数渡し済みコード。
- **初回改修**：装備する武器を切り替える。剣、弓、杖など。
- **ヒント案**：「勇者は今、どの武器を装備しているか分かる必要がありますよね？」
- **想定する実装**：勇者クラスに武器別の分岐・状態管理を追加。
- **追加改修**：剣の耐久度、弓の残弾数、杖の魔力消費など武器固有の状態と処理を追加。
- **狙うイラッと**：「武器を増やすたびに勇者のコードを修正するんか！ 状態まで勇者が管理するんか！」
- **解説**：武器自身に状態・振る舞いを持たせ、勇者には武器インスタンスを渡す。勇者は武器内部の詳細を知らずに使う。
- **重要な注意**：第3章の関数渡しにクロージャを組み合わせれば状態を保持できる。インスタンス渡しが常に優れているとは言えない。**この章が不自然なDI誘導にならないか最優先で検証**する。
- **歴史候補**：オブジェクトの協調、依存関係の分離、DIの普及。初期OOPと後年のDI用語を混同しない。

### 継承について【保留】

当初はクラスと継承を扱う案もあったが、現在の4段階（共通関数化→クラス化→関数渡し→インスタンス渡し）では継承を必須としない。無理に追加しない。必要性と時間を検証して判断。

## 5. 各章の標準進行【基本形】

1. その章の配布コードで開始する。
2. 小さな追加仕様を示し、参加者に改修させる。
3. 必要なら正しいが目先に寄ったヒントを提示する。
4. さらに仕様変更を出し、修正箇所の増加を体験させる。
5. 時間・到達状況を観察して作業を区切る。完成を要求しない。
6. 「どこが面倒だったか」を簡単に確認する。
7. **「実は昔、こんな事を言っていた人が…」**と歴史的背景を紹介する。
8. 一つの解決例を実演し、改修前後を比較する。
9. 次章用の共通完成コードに切り替える。

歴史紹介は各章3〜5分を仮置き。人物・引用・年代は、問題と解決例が確定してから原典に当たって検証する。先人の権威を理由に技術を採用させない。

| まとめ・質疑 | 15分 |
| **合計** | **180分** |

**計画の意味【合意済み】**：計画どおりにすべて実行することが目的ではない。何が起きる想定かを事前に把握し、現在の進行・参加者の状態・残り時間に問題があるか判断するための基準とする。進行台本には、各時点での想定到達状態、打ち切り・省略候補、時間超過時の判断材料を記載する。講師のアドリブに依存する分岐は増やさない。

## 7. 講師演出・締め【構想】

- 改修を依頼する際の軽い冗談：「では皆さん、この追加要望を満たすアプリに改修してください。その間私は……踊りますっ！！」
- 想定ツッコミ：「先生、ちょっと気が散るんですけどっ！！」。実際に踊るなら短時間で、課題進行を阻害しない。
- 歴史への転換：「実は昔、こんな事を言っていた人が…」
- 最後の種明かし：「オブジェクト指向開発ってね、こういうことなんですよ」
- 道具の使いどころの比喩：チェーンソーでキャベツの千切り／火炎放射器でタバコに火を点ける。
- 笑いは目的に資する演出。反応が薄くても説明を長引かせず先へ進む。

## 8. 歴史的引用の選定方針【合意済み】

- **今は各章の歴史テーマ候補だけを記録する**。人物、年代、引用の原文は教材仕様・解決例が固まった後で確定する。
- 可能なら一次資料・原典を確認する。原文と意訳を区別し、出典と発表年を残す。
- 現代の設計概念を過去の人物に安易に帰属させない。関数化・高階関数・OOP・DIの歴史を混同しない。
- 歴史の役割は「偉い人が言ったから正しい」ではなく、「同様の不便に対して先人がどう工夫したか」を伝えること。
- 原典が見つからない場合は創作の名言を作らず、一般的な歴史説明にとどめる。

## 9. 採用・却下・保留した判断

| 判断 | 状態 | 理由 |
|---|---|---|
| RPGを一つの題材として使う | 採用 | 架空仕様を柔軟に変えられ、ゲーム概念を理解しやすい |
| 4章を連続する一つのアプリで進める | 採用 | 変更要求による負担の蓄積と改善を実感できる |
| 「イラッと」を修正量に絞る | 採用 | 初学者に設計上の問題発見能力を要求しない |
| 完成しなくても打ち切る | 採用 | 成功条件は負担の体験と解決策の理解 |
| 各章後に共通コードを配布する | 採用 | 参加者ごとの実装差による進行破綻を防ぐ |
| 予想以上の正解に別ルートの追加課題を与える | **却下** | 講師の対応負荷・時間超過が増える。正解として認めて流す |
| 講師の即興対応を前提に構成する | **却下** | 想定外の環境・進行トラブルへの余力を残す |
| 電卓を題材にする | 見送り | 特に状態を持つインスタンス渡しの必然性が弱くなりやすい |
| 継承を必須項目にする | 保留 | 現在の4章構成では無理に入れる必要がない |
| 歴史上の人物・引用を今すぐ確定する | 後回し | 課題に歴史を無理に合わせることを避ける |

## 10. 技術検証・事前リハーサル【未着手】

各章について以下を確認する。

- [ ] 章の開始コードと、追加要求を満たす完成コードが実際に動く。
- [ ] 初学者が素直に実装した場合の修正箇所数・作業量を実測する。
- [ ] 紹介する解決策で、どの変更負担がどれだけ減るかを実測する。
- [ ] 最初から改善案を使った人がいても、講座の説明が破綻しない。
- [ ] 第2章はオブジェクトリテラルとクラスの役割を正確に区別できる。
- [ ] 第3章は関数渡しの利点を、追加要求によって明確に示せる。
- [ ] 第4章は関数＋クロージャとの比較で、インスタンス渡しの意義を誇張しない。
- [ ] 各章の終了コードが次章の開始コードと整合する。
- [ ] ブラウザ・エディタ・ローカル実行環境の事前確認手順を用意する。
- [ ] トラブル時にすぐ復旧できる各章の配布コードを用意する。
- [ ] 参加者の操作時間、解説、歴史紹介、笑い、休憩を含めて通しリハーサルする。
- [ ] 主催者に提案するための概要、所要時間、必要環境を整理する。

## 11. 次の制作工程

1. 4章を通したRPGの**最終仕様**を仮設計する（画面・状態・行動・武器の関係）。
2. 最終形から逆算して、各章の開始コード、初回要求、誘導ヒント、追加要求、解決例を具体化する。
3. 各章で「初心者が選びそうな実装」と「紹介する改善後の実装」の双方を作って比較する。
4. 想定どおりの修正負担が発生しない章は、要求や章構成を見直す。
5. 各章に対応する歴史的背景を一次資料等で検証し、出典を記録する。
6. 時間配分・講師台本・配布物を作成し、通しリハーサルする。
7. 主催者への企画提案、了承後にプレゼン資料と教材を仕上げる。
