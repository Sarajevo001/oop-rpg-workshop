## 1. 企画の目的と思想【合意済み】

JavaScriptの基礎を理解した参加者が、単純なRPGの改修を通じて、**修正箇所が多くて面倒くさいという不満**を実感し、その直後に先人が蓄積してきた設計上の工夫を知るハンズオン。

- 「オブジェクト指向開発」を、名前を覚えて従う万能の方法論として扱わない。
- 技術は、実際の不便や問題を減らすために発展した道具として扱う。
- 参加者に高度な設計能力や「設計とは何か」を語る能力を要求しない。無意識に行っている設計判断を出発点にする。
- 目標は課題の完成ではない。**「何か所も修正するのが嫌だ」→「その面倒を減らす工夫があるのか」**という体験。
- 参加者に自力で設計原則を発見させる必要はない。合理的だが後の変更に弱い実装を試す経験を重視する。
- 最後に、複数の工夫の共通した動機を明かす。締めの台詞案：**「オブジェクト指向開発ってね、こういうことなんですよ」**。
- 技術の使いどころを間違える例として「チェーンソーでキャベツの千切り」「火炎放射器でタバコに火を点ける」を使う構想。パターンの機械的適用や過剰設計への戒め。

## 2. 対象者・環境【概ね合意済み】

- 対象：変数、関数、if文などのJavaScript基礎が分かり、電卓程度の単体ブラウザアプリを作れる人。オブジェクト指向の知識は前提にしない。
- 各自ノートPCを持参し、ローカルのJavaScriptをブラウザで実行する。
- 題材：シンプルなRPG戦闘ゲーム。架空の仕様なので追加要求を柔軟に作れる。勇者、敵、HP、武器、魔法など直感的な概念を使用。
- UIや画面表示の土台は配布側で用意し、設計課題と無関係な画面実装で時間を消費させない方針（詳細未確定）。
- 開催時間は150〜180分程度を仮置き。主催者への提案は、教材と時間配分の検証後。

## 3. 教材設計・誘導の原則【合意済み】

1. **一本道**：第0章の導入後、4章を順に進める。個人別の別ルート課題は設けない。
2. **合理的な近道**：講師は事実として正しいヒントを出し、当面は正しく動く実装を促す。嘘の説明や意図的なバグで困らせない。
3. **後続の要求で負担が顕在化**：修正箇所・繰り返し作業が増える追加仕様を与える。参加者が設計の欠陥を言語化できる必要はない。
4. **イラッとの対象を限定**：狙うのは「同じような箇所を大量に直さないといけない」不満。「問題文が分からない」「環境が動かない」「教材にバグがある」は狙わない。
5. **未完成で終了可**：制限時間に達したら打ち切ってよい。完了率より、想定した負担に到達したかを観察する。
6. **先回りした正解は認める**：「あ、それ、正解です」で受け止め、講座の進行を分岐させない。想定外の合理的実装を否定しない。
7. **章ごとに共通ベースへ復帰**：講師が提示する解決例を説明し、次章は全員が同一の配布コードから開始。各自の実装差を累積させない。
8. **解決策の効果を見せる**：改修前後の変更箇所数・作業量・影響範囲を比較する。可能なら改善後に同種の変更を短く体験させる。
9. **正解の押しつけを避ける**：複数の妥当な設計があり得ることを認める。紹介する技術が唯一解とは言わない。

## 4. 章構成【ストーリー方針合意済み・課題とコードは仮案】

### 基準となる既存プレゼンと物語の軸【合意済み】

- 参照資料：『新たに類似のクラスを 作成する際の選択肢』（28ページ、Sarajevo001）。
- **元プレゼンの進化をRPGで再現する**。①類似の子クラスを増やす → ②プロパティを追加する → ③ファンクションを引数で渡す → ④インスタンスを引数で渡す、という比較の筋道を守る。
- RPG内では、**「仲間にしたスライム」**を全章を通して繰り返し登場させる。追加要求のたびにまたこのスライムが問題になる、という軽いキャラクター性・笑いも活用する。笑いの具体的な演出は未確定。
- 章ごとに別の問題へ飛ぶのではなく、同じスライムの「所属・操作方法・思考ルーチン・個体別の状態」を順に拡張する。
- **各章の課題1はその時点の自然な実装、課題2はその限界の顕在化、正解提示は次の設計への進化**を担う。課題2で本当に「イラッと」が発生するかは実装・リハーサルで検証する。
- 最終到達点はDI。ただし「DIが唯一の正解」ではなく、差異を子クラス・プロパティ・関数・状態付きインスタンスのどれで表現するかという設計上の選択を理解する。

### 第0章：クラスとインスタンスの導入【進行方式合意済み】

- **進行**：①正解提示 ②追加解説（歴史や偉人の話）のみ。受講者の実装課題は設けない。
- **正解提示案**：RPGのキャラクターを例に、クラス・インスタンス・プロパティ・メソッド・生成の最低限を、動くコードで紹介する。
- **追加解説案**：Simula等の歴史的背景を扱う。クラスは現実の物の分類を機械的に継承階層へ写すためだけのものではなく、要求に応じて状態と振る舞いを管理する手段の一つと説明する。
- **検証事項**：初心者が後続のクラスコードを読み改修できる最低限の説明範囲・時間。

### 第1章：類似クラスのコピーと重複【課題案・要検証】

- **元プレゼン対応**：①新たに子クラスを作成する（3〜5ページ）。
- **初期コード提示**：勇者と敵スライムが戦う。クラスを含む共通コードを配布。
- **課題1提示**：「敵スライムを仲間にし、味方として戦わせる」。既存のスライムをコピーして仲間スライム用の類似クラスを作る実装が自然に出るか検証。
- **各自実装**：コピー・派生等で要求を実現。
- **課題2提示**：「敵スライムにも仲間スライムにも共通する仕様を変更する」。
- **各自実装（イラッと）**：ほぼ同じコードを複数箇所で直す負担を体験する。
- **正解提示**：スライムの実装を共通化し、所属の違いを `team` 等のプロパティで表す（次章につなぐ）。
- **追加解説**：重複と再利用、クラスを増やすことの適否、関連する歴史的背景（人物・出典は未確定）。
- **要検証**：コピーを選ぶ必然性と変更箇所数。既存の第1章「共通関数化」コードは今回のストーリーとは別案として保持。

### 第2章：プロパティによる違いの表現と限界【課題案・要検証】

- **元プレゼン対応**：②プロパティを追加する（6〜13ページ）。
- **初期コード提示**：第1章の共通化済みスライムと `team` を引き継ぐ。
- **課題1提示**：敵味方を判定し、同じ陣営への攻撃を防ぐなど、`team` に基づく条件分岐を実装する。
- **各自実装**：所属の値で動作を切り替える。
- **課題2提示**：仲間スライムをプレイヤー操作、敵スライムをCPU操作とし、さらに「味方だがCPU操作」等を要求する。
- **各自実装（イラッと）**：所属と操作方式を同一視すると条件分岐・例外が増え、`team` だけでは操作方法を決められなくなる。
- **正解提示【章間接続を要検証】**：所属と操作方式を分離する必要性を示す。次章で「思考ルーチンを関数として外から渡す」解決へつなぐ。**第2章でどこまで実装を提示し、第3章の課題を何にするかは未確定**。
- **追加解説**：プロパティによる差異の表現は有効だが、条件分岐ですべての振る舞いを管理するのには限界がある。関連する歴史的背景は未選定。
- **要検証**：課題2で自然な修正負担が発生するか。第2章の正解提示と第3章の課題が重複しないか。

### 第3章：思考ルーチンを関数として渡す【課題案・要検証】

- **元プレゼン対応**：③ファンクションを引数で渡す（14〜18ページ）。
- **初期コード提示**：所属によってキー入力／CPUロジックを `if` / `switch` で選ぶ構成（第2章との接続を調整する）。
- **課題1提示**：仲間スライムと敵スライムで操作方法を切り替える。
- **各自実装**：条件分岐で実現するなど、当面の要求を満たす。
- **課題2提示**：所属と独立した操作方法（CPU操作の味方、別種の操作ルーチン等）を追加する。
- **各自実装（イラッと）**：操作方法を増やすたび既存の分岐を修正する。
- **正解提示**：思考ルーチンを関数として生成時等に渡す。キャラクター側は操作方式の内部事情を知らない。
- **追加解説**：関数渡し・振る舞いの差し替えの背景。高階関数をOOP固有の発明とは説明しない。
- **要検証**：**第2章の課題2と重複しているため、具体的な課題分割は要再設計**。関数を渡す解決が「正解提示」の段階で初めて必要になる流れを作る。

### 第4章：状態付き思考ルーチンのインスタンスを渡す【課題案・要検証】

- **元プレゼン対応**：④インスタンスを引数で渡す（19〜24ページ）、DIの効果（25〜27ページ）。
- **初期コード提示**：第3章の関数渡し済みスライム。
- **課題1提示**：複数の敵スライムが、一定時間ごとに方向・行動を変更する。
- **各自実装**：共通の関数と個体識別子・配列等で行動時刻を管理する実装を想定。
- **課題2提示**：敵をさらに増やし、各個体で独立した行動時刻・間隔を持たせる。
- **各自実装（イラッと）**：思考ルーチンの外側に個体別の時刻や識別子の対応関係を維持する負担が増える。
- **正解提示**：個体ごとに状態を持つ思考ルーチンのインスタンスを生成し、キャラクターへ渡す。DIの一例として説明する。
- **追加解説**：DI、依存関係の分離、条件分岐削減、機能の組み合わせ。DIの歴史は初期OOPと混同せず別途検証。
- **重要な留保**：関数＋クロージャでも個体別の状態を保持できる。インスタンス渡しだけが唯一解ではない。実際の操作時間・時刻管理が教材の主題を邪魔しないか検証する。

### 旧案と継承の扱い【履歴として保存】

- v0.3〜v0.5の第1章「共通関数化」、第2章「並行配列／HPと責務」、第3章「炎・氷・回復などの行動」、第4章「武器固有の状態」は、**新しい一貫した物語に置き換える**。旧コード・検証記録は比較素材として残し、現行教材の確定版とは扱わない。
- 元プレゼンには子クラスの比較があるが、継承の詳細講義を追加するかは保留。第0章で必要最低限を説明する範囲を検証する。

## 5. 各章の標準進行【合意済み】

**第1〜第4章は以下の7段階を、この順序で進める。**

1. **初期コード提示**：その章の共通コードを配布する。
2. **課題1提示**：自然に実装できる追加要求を提示する。
3. **各自実装**：受講者が課題1を実装する。
4. **課題2提示**：課題1の設計の限界が現れる追加要求を提示する。
5. **各自実装（イラッとポイント）**：受講者が修正負担を体験する。未完成でも時間で区切ってよい。
6. **正解提示**：その章の推奨改善例を示し、変更負担を比較する。唯一解とは断定しない。
7. **追加解説**：歴史や偉人の話、適用条件・限界を紹介する。

**第0章のみ**「正解提示 → 追加解説（歴史や偉人の話）」の2段階。実装課題なし。

各章の終了後は次章用の共通コードに切り替える。歴史紹介は各章3〜5分を仮置き。人物・引用・年代は教材の検証後に原典で確認する。

**計画の意味【合意済み】**：計画どおりにすべて実行することが目的ではない。何が起きる想定かを事前に把握し、現在の進行・参加者の状態・残り時間に問題があるか判断するための基準とする。進行台本には、各時点での想定到達状態、打ち切り・省略候補、時間超過時の判断材料を記載する。講師のアドリブに依存する分岐は増やさない。

## 7. 講師演出・締め【構想】

- 改修を依頼する際の軽い冗談：「では皆さん、この追加要望を満たすアプリに改修してください。その間私は……踊りますっ！！」
- 想定ツッコミ：「先生、ちょっと気が散るんですけどっ！！」。実際に踊るなら短時間で、課題進行を阻害しない。
- 歴史への転換：「実は昔、こんな事を言っていた人が…」
- 最後の種明かし：「オブジェクト指向開発ってね、こういうことなんですよ」
- 道具の使いどころの比喩：チェーンソーでキャベツの千切り／火炎放射器でタバコに火を点ける。
- 笑いは目的に資する演出。反応が薄くても説明を長引かせず先へ進む。

## 8. 歴史的引用の選定方針【合意済み】

- **今は各章の歴史テーマ候補だけを記録する**。人物、年代、引用の原文は教材仕様・解決例が固まった後で確定する。
- 可能なら一次資料・原典を確認する。原文と意訳を区別し、出典と発表年を残す。
- 現代の設計概念を過去の人物に安易に帰属させない。関数化・高階関数・OOP・DIの歴史を混同しない。
- 歴史の役割は「偉い人が言ったから正しい」ではなく、「同様の不便に対して先人がどう工夫したか」を伝えること。
- 原典が見つからない場合は創作の名言を作らず、一般的な歴史説明にとどめる。

## 9. 採用・却下・保留した判断

| 判断 | 状態 | 理由 |
|---|---|---|
| RPGを一つの題材として使う | 採用 | 架空仕様を柔軟に変えられ、ゲーム概念を理解しやすい |
| 4章を連続する一つのアプリで進める | 採用 | 変更要求による負担の蓄積と改善を実感できる |
| 「イラッと」を修正量に絞る | 採用 | 初学者に設計上の問題発見能力を要求しない |
| 完成しなくても打ち切る | 採用 | 成功条件は負担の体験と解決策の理解 |
| 各章後に共通コードを配布する | 採用 | 参加者ごとの実装差による進行破綻を防ぐ |
| 予想以上の正解に別ルートの追加課題を与える | **却下** | 講師の対応負荷・時間超過が増える。正解として認めて流す |
| 講師の即興対応を前提に構成する | **却下** | 想定外の環境・進行トラブルへの余力を残す |
| 電卓を題材にする | 見送り | 特に状態を持つインスタンス渡しの必然性が弱くなりやすい |
| 継承を必須項目にする | 保留 | 現在の4章構成では無理に入れる必要がない |
| 歴史上の人物・引用を今すぐ確定する | 後回し | 課題に歴史を無理に合わせることを避ける |

## 10. 技術検証・事前リハーサル【未着手】

各章について以下を確認する。

- [ ] 章の開始コードと、追加要求を満たす完成コードが実際に動く。
- [ ] 初学者が素直に実装した場合の修正箇所数・作業量を実測する。
- [ ] 紹介する解決策で、どの変更負担がどれだけ減るかを実測する。
- [ ] 最初から改善案を使った人がいても、講座の説明が破綻しない。
- [ ] 第0章でクラスの基礎を説明し、第1章のコードを受講者が扱える。
- [ ] 第2章と第3章の課題2が重複せず、関数渡しの必要性を段階的に示せる。
- [ ] 第4章は関数＋クロージャとの比較で、インスタンス渡しの意義を誇張しない。
- [ ] 各章の終了コードが次章の開始コードと整合する。
- [ ] ブラウザ・エディタ・ローカル実行環境の事前確認手順を用意する。
- [ ] トラブル時にすぐ復旧できる各章の配布コードを用意する。
- [ ] 参加者の操作時間、解説、歴史紹介、笑い、休憩を含めて通しリハーサルする。
- [ ] 主催者に提案するための概要、所要時間、必要環境を整理する。

## 11. 次の制作工程

1. 第0〜4章を通したRPGの**最終仕様**を仮設計する（仲間スライム・所属・操作方法・思考ルーチン・個体別状態の関係）。
2. 元プレゼンの4段階と7段階の章内進行を守り、各章の初期コード・課題1・課題2・正解提示を具体化する。**特に第2章と第3章の課題重複・共通コードの接続は要再検討。**
3. 各章で「初心者が選びそうな実装」と「紹介する改善後の実装」の双方を作って比較する。
4. 想定どおりの修正負担が発生しない章は、要求や章構成を見直す。
5. 各章に対応する歴史的背景を一次資料等で検証し、出典を記録する。
