# 第4章「仲間スライム、お前の頭の中まで管理するんか！」

- `starter/`：第3章 `solution/` とHTML・JS完全一致。
- `task1/`：敵A/Bの攻撃対象の選択方針（HPが低い相手／高い相手）を個体別変数 `enemyModeA`・`enemyModeB` と条件分岐で管理する素直な実装例。
- `task2/`：敵Cを追加し、`enemyModeC`・条件分岐・リセット処理を追加する実装例。
- `solution/`：敵スライムの配列と、個体ごとに注入した `AlternatingTargetController` を使う改善例。

各コントローラーは `preferLowest` を自身で保持し、行動するたびに切り替える。**2・3・4ターンという根拠のない切替間隔設定は撤廃**した。敵を含む全キャラクターは単一の `characters` 配列で管理し、攻撃対象選択肢と敵の表示を配列から生成する。死亡した味方は攻撃しない。

## 第2章から引き継ぐ設計

第2章で導入した単一の `characters` 配列を継続使用。敵と味方は `team` と生存状態で抽出し、表示と攻撃対象の選択肢は配列から生成する。第4章ではキャラクター管理の再設計を課題にせず、各コントローラーに行動状態を保持させる責務分離に集中する。

## 後続改修の反映（2026-10-24）

全キャラクターを単一のcharacters配列で管理し、teamとhpで敵味方・生存者を抽出する。勇者・魔法使い・プレイヤー操作中の仲間スライムは共通の選択対象を攻撃する。仲間スライムのCPU切替ではコンボボックスを無効化しない。HP0の敵は選択肢から除外し、選択対象が倒れたら生存する先頭の敵へ切り替える。カードは絵文字・名前・HPを動的生成し、ターン別ログは新しいものを上に配置する。

## 第3章からの関数注入の継続（2026-10-24）

第3章改善例では `Slime` インスタンスに操作関数を注入する。第4章の `starter/` はそのコードをそのまま引き継ぐ。`task1/`・`task2/` は仲間スライムの `controller` を維持しつつ、敵の選択方針を個体別の `enemyModeA`・`enemyModeB`（課題2では `enemyModeC` も）と条件分岐で管理する。`solution/` では敵ごとに `AlternatingTargetController` オブジェクトを注入し、`preferLowest` を各オブジェクトに保持する。仲間スライムは関数注入のままとし、関数と状態付きオブジェクトの比較を第4章の焦点とする。

## 勇者・魔法使いへの操作関数注入（2026-10-24）

第3章完成版から引き継ぎ、勇者・魔法使いも `controller` を保持する。味方全員の行動は共通ループで処理する。第4章課題1・2では敵の対象選択のみ個体別変数と分岐を使用し、完成版では敵ごとの状態付きコントローラーへ移行する。

## 課題1・2の素直な実装例と変更負担（2026-10-25）

課題1では敵A・Bが「HPの低い相手／高い相手」を攻撃ごとに交互に選ぶ。中央に `enemyModeA`・`enemyModeB` を置き、敵名による分岐で各状態を更新する。課題2では敵Cを追加するため、(1) `characters` の生成要素、(2) `enemyModeC` 宣言、(3) 対象選択分岐、(4) リセット時の初期化の4箇所に手を入れる。改善例では `AlternatingTargetController` の個別インスタンスを敵Cに渡す生成要素の追加のみで対応できる（既存の状態管理処理への変更は不要）。この4対1は当該実装例の比較であり、全ての解法に当てはまる数値ではない。

`Map` やクロージャで個別状態を適切に管理する実装も正解として認める。課題は悪いコードを強制するものではなく、素直に個体別変数・分岐で実装した場合の変更負担を比較する。単一の `characters` 配列、動的UI、味方の関数注入は維持する。課題1・2の敵には第3章由来の `cpuControl` が渡されるが、課題用の敵ターンは `centrallyControlledTarget` を使用する。これは課題用の一時的な不統一であり、改善例で敵のコントローラーを利用する設計に戻す。
